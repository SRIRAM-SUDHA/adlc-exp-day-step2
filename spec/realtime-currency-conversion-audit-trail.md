**Title:** Real-Time Currency Conversion & Audit Trail

**Business Idea:** Treasury operations teams at our enterprise customers
currently convert currency using manual lookups against a third-party
portal — slow, and it leaves no record for compliance. We need instant,
self-serve conversion inside our own app, and because these are regulated
transactions, every conversion must be reconstructable for an auditor on
demand, not pieced together afterward from emails or spreadsheets.

**Persona:** Treasury operations analysts at enterprise customers, who
process multiple cross-border settlements a day and are personally
accountable if a conversion can't be justified during an audit.

**User Need:** See a trustworthy converted amount the moment I enter it
— and be able to pull up any past conversion, with its rate and timestamp,
the moment an auditor asks for it.

**Known Constraints:**
- Frontend must read `VITE_API_URL` dynamically at container runtime using
  a generic entrypoint script placeholder replacement; replace the placeholder token
  `__VITE_API_URL__` inside the built `index.html` (or equivalent) with the runtime
  `VITE_API_URL` value.
- Backend must read database configurations exclusively from runtime
  environment variables.
- Backend must query external currency conversion data exclusively using a base URL from an environment variable (`CURRENCY_API_BASE_URL`), defaulting to an unauthenticated open-source endpoint like Frankfurter (`https://frankfurter.dev`).
- The application must not hardcode third-party API response schemas; utilize flexible JSON property mapping or an abstraction layer to isolate internal compliance tracking from external JSON structure changes (such as `rates` vs `conversion_rates`).
- The audit trail record must capture the exact execution timestamp generated by your backend server alongside any date or sequence markers returned by the external provider, ensuring complete sub-second audit reconstruction even if the provider only exposes a calendar date.
- External HTTP calls must handle failures gracefully with fallback values or clear domain exceptions rather than bubbling up raw network or serialization errors.
- CI/CD pipeline must inject placeholders safely at deployment time without
  exposing sensitive data in container layers.
- Restricted to specific stack versions: React (Vite/Node 24.*) and C#
  (**backend must target `net10.0` for build/test; CI must use `dotnet-version: 10.0.x`**).
- Must adhere to a strict folder layout (`src/frontend` and `src/backend`).
- A .NET solution file must always be generated at `src/backend/OuterloopLabApi.sln` via `dotnet new sln` + `dotnet sln add`, with the backend project added to it, and CI/build/test commands must invoke this `.sln` rather than the `.csproj` directly.
- Deploy as a single Azure Container App using the sidecar pattern to host
  both frontend and backend.
- Authenticate to Cosmos DB exclusively using token-based authentication via the pre-assigned User-Assigned Managed Identity, instantiated using `DefaultAzureCredential` configured with the specific `ManagedIdentityClientId`. Absolutely zero connection strings, master keys, or account keys are permitted in code, configurations, or logs.
- Utilize `Microsoft.Azure.Cosmos` and `Azure.Identity` packages for
  secure, token-based database interactions, including data-plane CRUD operations like adding and deleting items.
- Include `Azure.ResourceManager` and `Azure.ResourceManager.CosmosDB` packages to programmatically provision the Cosmos DB database and container via the control plane inside the application startup lifecycle (`Program.cs`) before the web application runs, utilizing the same token-based Managed Identity credentials for authentication.
  - ARM provisioning is best-effort; Managed Identity RBAC for ARM may differ from data-plane RBAC.
  - CRUD (and data-plane creation if needed) must be done via the Cosmos SDK (data-plane) using token-based Managed Identity credentials; access keys must not be used.
  - After ARM attempt, startup must run token-authenticated data-plane `CreateDatabaseIfNotExistsAsync` and `CreateContainerIfNotExistsAsync` and only proceed if the database/container are available (either already exist or were created). If token-authenticated data-plane create-if-not-exists fails, startup must fail.
- Map and bind all configuration values, including `AZURE_MANAGED_IDENTITY_CLIENT_ID`, endpoint URLs, and resource names, directly from the environment variables **using the exact keys** defined in `docs\CONTAINER_ENVIRONMENT_VARIABLES.md` without using local settings configuration files as fallbacks.

**Current Context:** `src/backend/Program.cs` must bind the exact environment variable keys documented in `docs\CONTAINER_ENVIRONMENT_VARIABLES.md`, construct `DefaultAzureCredential` with `ManagedIdentityClientId`, perform best-effort ARM Cosmos provisioning, then call token-authenticated `CreateDatabaseIfNotExistsAsync` and `CreateContainerIfNotExistsAsync` before the web app starts; `src/backend/OuterloopLabApi.sln` must include the backend project and be the entry point for build and test commands; `src/backend/OuterloopLabApi.csproj` is assumed for planning purposes if the project file name is not otherwise specified, but the actual backend project file under `src/backend` must target `net10.0` and reference the required Azure/Cosmos packages; `src/frontend/index.html` (or the generated equivalent) must preserve the `__VITE_API_URL__` placeholder for runtime replacement; `src/frontend/package.json`, `src/frontend/src/main.tsx`, and `src/frontend/src/App.tsx` must support a Vite UI that reads the runtime-injected API base URL and exposes both conversion entry and audit retrieval flows.

**In Scope:**
- Add a backend `POST` API in `src/backend` that accepts an amount, source currency, and target currency; calls the external rate provider through a dedicated abstraction; returns the converted amount plus audit metadata.
- Persist one immutable audit record in Cosmos DB for each successful conversion, including the original request values, provider rate, provider date/sequence marker if present, exact backend execution timestamp, and a server-generated audit identifier.
- Add backend retrieval APIs in `src/backend` for looking up a stored conversion by audit identifier and for listing recent conversions with simple filters suitable for an auditor-facing lookup screen.
- Add a React/Vite flow in `src/frontend` that lets the user enter a conversion request, see the converted amount immediately, and open previously stored conversion records with their rate and timestamps.
- Wire startup, configuration binding, and runtime placeholder replacement so the feature works in the required sidecar deployment model with all values coming from environment variables.
- Handle upstream provider failures with domain-safe API responses instead of leaking raw HTTP, socket, or JSON exceptions.

**Out of Scope:**
- Supporting multiple external conversion providers or provider failover orchestration beyond the single configurable base URL.
- Importing historical conversions from spreadsheets, email archives, or third-party systems.
- Adding authentication, authorization, or persona management beyond whatever already exists in the application shell.
- Building PDF, CSV, or email export workflows for auditors.
- Implementing rate caching, speculative prefetching, or scheduled background refresh jobs.

**Feature Constraints:**
- Use `IHttpClientFactory` with a typed client or narrow provider adapter in `src/backend` so external currency calls are isolated from controllers/endpoints and can translate provider payloads into an internal conversion model.
- Map provider JSON through flexible DTO/property-handling logic or an adapter that can tolerate field-name variation; the rest of the application must not depend directly on provider-specific fields such as `rates`.
- Use `decimal` for monetary amounts and rates, normalize currency codes to uppercase ISO-style strings, return display amounts rounded to 2 decimal places, and store the provider rate with its full available precision for audit reconstruction.
- Generate the audit identifier on the backend and return it in the conversion response so the exact stored record can be fetched later without recomputing the conversion.
- Return RFC 7807 `ProblemDetails` responses for invalid requests and upstream/provider failures; use `400` for invalid amount/currency input and `503` when the provider call cannot produce a trustworthy quote.
- Treat persisted audit records as append-only evidence: retrieval must read the stored Cosmos document and must never recalculate historical converted amounts from a new live rate.

**Expected Outcome:** When a user submits a conversion such as `100.00` from `USD` to `EUR` and the configured provider returns a rate of `0.92` with a provider marker like `2026-08-01`, the backend returns `200 OK` with a payload containing a server-generated audit ID, `sourceAmount: 100.00`, `sourceCurrency: "USD"`, `targetCurrency: "EUR"`, `convertedAmount: 92.00`, `rate: 0.92`, `providerMarker: "2026-08-01"`, and an exact `backendExecutedAtUtc` value such as `2026-08-01T10:15:30.123Z`; the same values are written to Cosmos DB and later returned unchanged by the audit retrieval API and frontend audit view. If the provider is unavailable or its payload cannot be mapped into the internal conversion model, the conversion API returns a `ProblemDetails` response with status `503` and a domain-safe error message, with no raw network, timeout, or serialization exception text in the response.

**Expected Agent Output:** OpenCode should produce a multi-file implementation under `src/backend` and `src/frontend`, including backend API/persistence changes, frontend conversion and audit UI changes, any required runtime placeholder-replacement script updates for `__VITE_API_URL__`, and verification steps showing the frontend build succeeds and the backend build/test commands run against `src/backend/OuterloopLabApi.sln` rather than a `.csproj` directly.

**Suggested Intent For OpenCode:** Implement the currency conversion and audit-trail feature described in this Spec across `src/backend` and `src/frontend`, but do not violate any Known Constraint: keep the strict folder layout, target `net10.0`, ensure `src/backend/OuterloopLabApi.sln` is used for build/test, bind all required configuration from the exact environment variable keys defined in `docs\CONTAINER_ENVIRONMENT_VARIABLES.md`, read the external provider base URL from `CURRENCY_API_BASE_URL`, preserve runtime replacement of `__VITE_API_URL__` in the frontend, use `DefaultAzureCredential` with the specified `ManagedIdentityClientId` for both best-effort ARM provisioning and required Cosmos data-plane create-if-not-exists plus CRUD, never use connection strings or keys, never hardcode third-party response schemas, and implement clear `ProblemDetails` error handling while returning stored immutable audit records for later lookup.
